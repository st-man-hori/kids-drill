# architecture

## 概要

サービス名は「キッズドリルゲーム」、ドメインは`kids-drill-game.st-man.com`、リポジトリ名は`kids-drill`。算数ドリル学習サービス。小学1年生のたし算・ひき算から始め、小学1〜6年生の算数（四則演算・分数・小数・割合・図形・代数の初歩など）まで拡張予定。現在は国語のかんじよみクイズ（小1〜4対応）も先行して実装済み（下記「かんじよみクイズ（v1）」参照）。

**サービス名とドメインに教科名を入れない**のは意図的。当初は「さんすうチャレンジゲーム」「math-challenge-game」だったが、漢字のよみのように算数以外へ広げる可能性が出てきたため、名前で自分を縛らない形に変えた。ドメイン変更はPWAのホーム画面追加が広まってからだと貼り直しを強いることになるので、早い段階で寄せている。

教科を算数から始めるのは意図的な判断。算数はパラメータからの動的な問題生成でほぼ全範囲をカバーでき、個人開発の工数でも小6まで現実的に到達できる。一方、国語などの他教科は漢字・語彙・読解のように実データのキュレーションが必要でコスト構造が大きく異なるため、現時点では計画していない。DBの`subjects`テーブルはレコード追加のみで教科拡張できる設計になっており、将来本当に必要になれば対応できる（＝今からその前提でアーキテクチャを複雑にする必要はない）。

**漢字のよみだけは例外的に検討の余地がある。** 学年別漢字配当表は公開された固定データで小1なら80字と有限なので、上の「キュレーションのコストが高い」という理由が当てはまりにくい。ただし壁はデータではなく**回答の入力方式**にある。現在の練習エンジンは数値専用（`generateQuestions`が`{a, b, answer: number}`を返し、入力は数字パッド）で、かなキーボードを子どもに出すのはPINを数字にしたのと同じ理由で無理。載せるなら多肢選択（4択）の回答UIを足す必要がある。一方でレベル昇降・ポイント・演出・着せ替えの解放条件は`skill_type`ベースで教科に依存していないため、報酬まわりはそのまま流用できる。

着手の順序としては、算数側（ひき算・タイムアタック・ランキング）が揃うまでは広げないとしていたが、ユーザーの明示的な指示により先行して着手した（下記）。

### かんじよみクイズ（v1）

`/practice/kanji`に、配当漢字の読み4択クイズを実装した。上の「壁は回答の入力方式にある」という課題を解決する形で多肢選択UIを追加している。

**問題データの作り方**（`scripts/kokugo-ai/generate-distractors.ts --grades=1-6`、手動実行）:

1. 教育漢字API（`api.kyoiku-kanji.st-man.com`、認証不要、`limit`上限1026＝学年配当表1〜6年の合計字数）から学年別の漢字データ（読み・用例）を取得
2. 各漢字について、出題する読みとその文脈の候補を集める（`scripts/kokugo-ai/lib/select-reading.ts`の`selectReadingCandidates`）。**「この字単体の読みは？」は複数読みを持つ字で問いが一意に決まらない**（「大」はタイ/ダイどちらも正しい）ため、対象の字が先頭または末尾にある用例を探し、ふりがな全体から対象の字ぶんの読みだけを前方一致／後方一致で切り出す。中間位置の用例は境界が一意に決まらないため対象外。切り出せた読みは`maskedReading`（例:「大学」→`○○がく`）として設問そのものに含め、AIが生成した誤答が実は別の場面で正しい読みだった、という事故を構造的に防いでいる（学年1〜6合計1026字中1004字でこの方式が成立した）
3. 条件を満たす用例が2件以上ある字は、まず用例の「かんじ部分」の文字数（ふりがな除く）が3字以内の候補があればそれを機械的に採用する（`scripts/kokugo-ai/lib/select-example-difficulty.ts`）。教育漢字APIの`examples`はやさしい語から並んでいるとは限らず、対象漢字の画数（＝難易度軸、後述）は小さくても用例自体が「一朝一夕」のような四字熟語で学年不相応に難しくなることがあったため、単純な「先頭の用例を使う」から変更した。二字熟語程度の候補が1つでもあれば四字熟語より十分やさしいと判断できるので、さくらのAIは**候補がどれも4字以上（＝短い代替が存在しない）字だけ**に絞って呼び、「その学年の子にいちばんやさしいのはどれか」を判定させる（`pickEasiestExample`）。実測（学年1〜6・使用可能1004字）ではAI呼び出しが必要になるのは22字のみ。AI応答のパース失敗・エラー時は候補の中で最短の用例にフォールバックし、パイプラインは必ず完走させる
4. その読みに対する紛らわしい誤答を、さくらのAI Engine（OpenAI互換Chat Completions、`gpt-oss-120b`）に生成させる。1字1リクエストで3個ずつ・2ラウンド（＝1字あたり最大6個のプール）に分けて依頼し、毎ラウンド「すでに使った誤答」を伝えて重複を避けさせる。正解と同じ文字種か・正解に文字を継ぎ足しただけの水増しでないか等を検証し、崩れた項目は個別に1回リトライ、それでもダメなら決め打ちのフォールバック候補で必ず完走させる（`scripts/kokugo-ai/lib/build-distractors.ts`）。ラウンド数は元々3（プール9個・約3000リクエストでさくらのAI Engineの枠にちょうど収まる設計）だったが、上記の例文難易度判定を追加した分の予算を確保するため2に減らした（誤答約2000＋例文判定約20〜数十＝合計2000強）
5. 結果を`src/data/kanji-quiz/grade{1..6}.json`にコミットする。アプリはこの静的JSONを`import`するだけで、実行時にAPIやAIを呼ばない

Yahoo!テキスト解析APIは未使用。教育漢字APIが読みを構造化データで返すため、形態素解析で読みを抜き出す必要がなかった。

**誤答をプールにしてランダムサンプリングする**: JSONには1問あたり最大6個の誤答プール（`distractorPool`）を持たせ、実際の4択はプレイのたびに`src/lib/kanji-quiz.ts`の`buildKanjiChoices`がその中から3個をランダムに選ぶ。同じ字を何度解いても毎回同じ4択にならないようにするための設計で、これにより「定期実行で問題を洗い替える」必要がなくなった（配当漢字表自体はほぼ変わらないデータなので、内容を変えたい実益は薄い）。**生成は基本的に一度きりでよく、以降は明示的に内容を作り直したくなったとき（誤答の質を上げたい、学年配当表が変わった等）だけ`npm run quiz:kanji:generate`を再実行する想定。** 定期実行（GitHub Actions等）は検討したが、公開リポジトリのmainへAI生成物を無審査で自動コミットするのは子ども向けサービスとしてリスクが見合わないと判断し、見送っている。

**問題データをDBではなく静的JSONにした理由**: `difficulty_levels.config`のような「毎回同じロジックで解釈するパラメータ」と違い、こちらは生成にAI呼び出しというコストが伴う「コンテンツそのもの」。マイグレーションで管理するより「スクリプトで生成→レビューしてコミット」の方が実態に合っている。

**v1のスコープ**: ポイント・`practice_sessions`への記録・レベル昇降・着せ替え解放のすべてを、既存の報酬経済（`src/lib/practice-progress.ts`）にそのまま接続している。`practice_sessions.level_id`は算数もかんじも共通で必須のまま——`subject_id`・`skill_type`をテーブルに直接持たせる設計も一度検討したが、「レベルを持たないスキル」という特殊ケースのために`practice_sessions`の汎用性を落とすより、かんじにもレベルを持たせて既存の仕組みにそのまま乗せる方がシンプルと判断した。

**かんじの難易度軸には画数（`strokeCount`）を使う。** どの漢字を学校で習ったかはアプリから分からないため、算数の「繰り上がりの有無」のように**どの子にも共通して測れる指標**が要る。教育漢字APIは元々`strokeCount`を返しており、`src/data/kanji-quiz/grade{N}.json`の各設問にも持たせてある（`scripts/kokugo-ai/lib/kyoiku-kanji-client.ts`）。レベルは`KanjiLevelConfig.maxStrokeCount`（`src/lib/kanji-quiz.ts`）による画数の上限で区切り、**下限は設けない累積方式**（レベルが上がるほど出題プールが広がる＝すでに解けるようになった易しい字も引き続き出題対象に残る）。

**`practice_sessions.child_profiles.grade`と連動しており、学年ごとに別々のスキル・レベル表を持つ。** `skill_type`は`kanji_reading_grade1`〜`kanji_reading_grade4`のように学年でnamespaceしている（`kanjiSkillType(grade)`）。理由は学年ごとに配当漢字のバンク・画数分布がまったく違うため——`KANJI_LEVELS_BY_GRADE`（`src/lib/kanji-quiz.ts`）は学年ごとの画数分布をおよそ4等分する位置（累計字数がその学年の1/4・2/4・3/4に最も近い画数）から個別に決めている。grade1の区切り（3/4/6画）をそのまま他学年に使うと、学年が上がるほど字数・画数が増えるぶん偏った区切りになるため。5・6年生ぶんは問題バンクが未生成（`KANJI_SUPPORTED_GRADES = [1,2,3,4]`）で、対象外の学年は`difficulty_levels`の行も無いため`getCurrentLevel`を呼ばず、空の問題リストを返して既存の「もんだいが まだ ないみたい」表示に委ねている（`practice/kanji/page.tsx`・`actions.ts`）。`drizzle/0006_kanji_reading_levels.sql`が`subjects`に国語＝`kokugo`を追加し、学年別`skill_type`ぶんの`difficulty_levels`を投入する。

かんじの出題は算数のように無限生成ではなく固定バンクからの抽選（`prepareKanjiQuestions`）なので、`practice.ts`の`LevelConfig`のような「問題を生成するパラメータ」ではなく「固定バンクをフィルタする条件」としてconfigを使っている（`kanjiBankForLevel`）。レベル昇降の判定ロジック自体（`shouldLevelUp`・`isStrugglingSession`・`advanceToNextLevel`・`demoteIfStruggling`）は算数と共有しており、かんじ専用の実装は持たない。

結果画面の演出（`Celebration`・`celebrationTier`）も`src/lib/practice.ts`から流用している。報酬ループへの統合含め[game-design.md](./game-design.md)を参照。

## 認証設計

親アカウントという別レイヤーは持たず、アカウントは子どもごとの1つのみ。登録作業は親子一緒に行う（親が発行をサポートする）想定。

- 登録時にID（一意）とひみつのばんごう（6桁の数字PIN）を発行し、紙に書いて子どもに渡す運用
- PINは数字のみ・6桁。4桁＋レート制限でも実用上は十分（ATMのPINと同様の考え方）だが、親子で発行する認証情報として余裕を持たせて6桁に。英字混在にはしない（通常キーボード入力が必要になり、数字PINパッドUIの方針と矛盾するため）
- ID: DBで`UNIQUE`制約
- PIN: 平文保存せずbcryptでハッシュ化して保存
- ブルートフォース対策: Upstash Ratelimitでログイン試行回数を制限（IP/ID単位）
- ログイン失敗時、「IDが存在しない」か「PINが違う」かをレスポンスで区別しない（ID列挙対策）
- 入力UIはテキストキーボードではなく数字PINパッド（タッチ操作前提、6歳児でも操作しやすいUI）

## デプロイとマイグレーション

Vercelにはリリースフェーズ（ビルドとは別の、デプロイ直前に1回だけ走る枠）が存在しない。そのためスキーマ変更の適用はビルドコマンドに含める。`vercel.json`の`buildCommand`で明示している。

```
npm run db:migrate && next build
```

判断の理由:

- **`vercel.json`に書く**（Vercelダッシュボードの設定欄やpackage.jsonの`vercel-build`ではなく）。パブリックリポジトリなので、デプロイ時に何が走るかがリポジトリを見れば分かる状態を優先した。ローカルの`npm run build`は`next build`のみのまま保つ
- **マイグレーションは`drizzle-kit migrate`**。適用済みバージョンは`drizzle.__drizzle_migrations`テーブルで管理されるため、毎デプロイで実行しても未適用分だけが流れる
- **接続は非プール（直接接続）**。DDLをPgBouncer経由で流すのを避けるため、`drizzle.config.ts`は`DATABASE_URL_UNPOOLED`があればそちらを優先する。Vercel-Neon連携がこの変数を自動で設定する

### マスタデータもマイグレーションで投入する

教科・難易度レベルは、シードスクリプトを別途デプロイ時に走らせるのではなく**データマイグレーションとして`drizzle/`に置く**（`drizzle-kit generate --custom`で空のマイグレーションを作り、SQLを手で書く）。

一般に「seed」と呼ばれるのは開発・テスト用のダミーデータで、デプロイ時に自動実行しないのが通例（Rails `db/seeds.rb`、Prisma `db seed`とも用途をdev/testと明記している）。一方これらの行は**無いとアプリが起動時にthrowする**（`practice-progress.ts`）＝スキーマの契約の一部であり、その種のマスタデータはスキーマと同じ台帳でバージョン管理するのが定石（Djangoの`RunPython`データマイグレーション、Flyway/Liquibaseのreference dataスクリプトと同じ考え方）。

Vercelにはリリースフェーズもワンオフ実行の口（`heroku run`相当）も無いため、「確実に1回だけ・台帳付きで・スキーマ変更と一緒に走る」機構がマイグレーションしかない、という事情もこの選択を後押ししている。冪等性の担保やupsert、並行ビルド時の重複挿入といった問題が丸ごと発生しなくなる。

トレードオフとして、レベルの`config`は`src/lib/practice.ts`の`ADD_LEVELS`とマイグレーションSQLの2箇所に存在する。**実行時にアプリが読むのはDB側**なので、レベルを調整・追加するときは配列を直すだけでは反映されず、新しいマイグレーションを書く必要がある（その分、コンテンツ変更がPRの差分としてレビュー可能になる）。

なお、`difficulty_levels`には`(subject_id, skill_type, level_number)`のunique制約を張っていない。マイグレーション経由なら1回しか走らないため冪等性のためには不要だが、データ整合性の担保として将来足す余地はある（[data-model.md](./data-model.md)）。

### 環境ごとのDB

Production環境とPreview環境で**別のDBを使う**（PreviewはNeonのブランチ）。同じDBを共有すると、PRのプレビュービルドが本番のスキーマを書き換えてしまうため。分離されている前提なので、マイグレーションはProduction・Previewどちらのデプロイでも無条件に実行してよい構成にしている。

### 破壊的変更の扱い

マイグレーションは`next build`の前に走る。ビルドが失敗してもスキーマ変更は適用済みで、旧コードが動き続ける状態になりうる。カラム削除・リネームのような後方非互換な変更は、1回のデプロイで済ませず expand / contract（①新カラム追加 → ②両対応コードをデプロイ → ③旧カラム削除）に分けること。

## PWA（ホーム画面への追加）

**`next-pwa`は使わない。** Next.js標準の`app/manifest.ts`と`metadata.appleWebApp`で必要なものが揃うため、依存を増やす理由がない。

- iOSはマニフェストだけではフルスクリーン起動しないので、`appleWebApp`の指定が要る。メインターゲットがiPadなのでこちらが本命
- ホーム画面から起動したときの行き先は`/mypage`。案内ページを経由させない。ログインが切れていれば`/mypage`側がログイン画面へ送るので、ログアウト状態でも破綻しない
- 背景・テーマ色は画面の下地（`--color-base`）に揃える。起動時のスプラッシュやブラウザUIが本体と地続きに見えるようにするため
- 画面の向きは固定しない（縦横どちらでも遊べる設計。[design.md](./design.md)）

### 未対応
- **Service Workerは入れていない**（＝オフラインでは動かない）。iOS/iPadOSのホーム画面追加はService Workerなしで成立するため、当面の目的は満たせている。オフライン対応やAndroidのインストールバナーが必要になった時点で別途検討する。なおこのアプリはDBを前提としており、オフラインで意味のある機能がほぼ無い

## 公開・プライバシー方針

- リポジトリはパブリック公開予定
- 秘密情報（APIキー、DB接続文字列、NextAuthのシークレット等）は`.env.local`に置き`.gitignore`で除外し、ドキュメントにも記載しない
- アクセス解析にVercel Web Analyticsを使う。Cookieを使わず、訪問者を個人として識別・追跡しない方式のため、子どもが対象のサービスでも採用できると判断した。ルートlayoutに`<Analytics />`を置くだけの構成で、**アプリ側からユーザーを識別できる情報（ログインID・ニックネーム等）をイベントとして送らない**こと
