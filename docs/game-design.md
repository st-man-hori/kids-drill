# game-design

## コンセプト

紙のドリルにはない「デジタルである強み」を活かす。単一の報酬だけだとすぐ飽きるため、時間スケールの異なる報酬を重ねて設計する。

## 報酬ループ（多層構造）

| スケール | 仕組み |
|---|---|
| 1問ごと | 正解モーション・エフェクト |
| 1セッション内 | 連続正解コンボ演出 |
| 1セッション終了時 | 正解数に応じた結果画面の祝い演出（下記） |
| 中期 | ポイントを貯めて着せ替えアイテムと交換 |
| 長期 | 着せ替えアイテムを集めてコーディネート |
| 継続的比較 | 自己ベスト／ランキング（タイムアタックモード） |

### 結果画面の祝い演出

10問終わったときの演出を正解数で4段階に出し分ける。**しきい値はレベルの昇降とわざと揃える**（クラッカーが上がる＝レベルアップ圏、いちばん静かな段階＝降級圏）。演出の派手さと難易度の手応えがズレないようにするため、かつ恣意的なしきい値を増やさないため。

| 正解数 | 見出し | クラッカー |
|---|---|---|
| 全問 | ぜんもん せいかい！ | 左右2発 |
| 8〜9（レベルアップ圏） | すごい！ その ちょうし！ | 中央1発 |
| 5〜7 | よく がんばったね！ | なし |
| 0〜4（降級圏） | さいごまで やりきったね！ | なし |

- **どの段階でも否定的な言葉は使わない**（[design.md](./design.md): 恐怖感を与える演出は避ける）。演出の量で差はつけるが、成績が悪いことを言葉で突きつけはしない
- 見出しは行を追加するのではなく**「おつかれさま！」を置き換える**。行が増えると画面が伸びてスクロールが必要になるため（[design.md](./design.md)「スクロールなし方針」）
- クラッカーは絶対配置のオーバーレイでレイアウトに影響させない。`prefers-reduced-motion` では出さない

### ポイントの付与レート（練習モード）

- 正解1問につき **10ポイント**
- 10問すべて正解でさらに **50ポイント** のボーナス（1問も落とさないことに価値を持たせる）

着せ替えアイテムの価格が未定のため暫定値。アイテムのラインナップを決める時に、
「何セッションでどのくらい貯まるか」から改めてバランス調整する。

## 出題ロジック・難易度カーブ

難易度は「桁数」より「繰り上がり・繰り下がりの有無」を主軸に設計する（小学校算数で実際の壁になるのはここのため）。小1のたし算は例えばこう並べる（ひき算も同じ考え方で繰り下がりなし→ありの順）。

| Lv | 内容 | 例 |
|---|---|---|
| 1 | 1桁+1桁、繰り上がりなし（和≤10） | 3+4 |
| 2 | 1桁+1桁、繰り上がりあり（和11〜18） | 8+5 |
| 3 | 2桁(10〜19)+1桁、繰り上がりなし（和11〜19） | 10+7 |
| 4 | 2桁(11〜19)+1桁、繰り上がりなし | 13+4 |
| 5 | 2桁(11〜19)+1桁、繰り上がりあり（挑戦枠） | 18+5 |

Lv3は元々「10+1桁」固定だったが、aが常に10になり必ず同じ形の問題になってしまう不具合が
実プレイで見つかった（issue #5）。aを10〜19に広げて解消した。Lv4はLv3の
ほぼ部分集合（aの範囲が11〜19とわずかに狭いだけ）になるが、レベル数・既存の
到達判定を変えたくないため意図的にそのまま残している。

「2桁+2桁」以降は小2の範囲としてLv6以降に追加する。各レベルは`{min_a, max_a, min_b, max_b, carry}`のような設定データとして持たせ、コード変更なしでレベル追加できるようにする。レベルアップ判定は「直近10問中8問正解で次のレベルへ」を基準とする。たし算・ひき算は別々にレベル管理する。

### 降級

**10問中4問以下のセッションが2回続いたら、レベルを1つ下げる。**

昇級だけあって降級が無いと、まぐれで8問正解して上がった子が「毎回2〜3問しか解けないレベル」に固定され、自力で戻る手段が無くなる。ポイントも貯まらず着せ替えも解放されず、上の報酬ループが全部止まるため、離脱要因として最も太い。

- **4問以下**: 当てずっぽうでも当たる範囲を下回っている＝明確に手が出ていない水準
- **2回連続**: 眠い・気が散ったといった1回のコケで下げないため
- **判定対象は「今のレベルで解いたセッション」に限る**。降級直後は対象が0件になるので、1回の不調で下まで転げ落ちることはない
- Lv1からはそれ以上下げない

**降級は演出しない。** 「レベルが下がりました」という通知は子どもにとって罰であり、昇級の祝祭と対称に扱ってはいけない。黙って易しい問題が出るだけにする（昇級だけ盛大に祝う非対称でよい）。

**プレイ画面にレベル番号を表示しない。** 通知しなくても「レベル3」→「レベル2」という数字の変化は数字が読める子には見えてしまい、結局「下がったこと」を突きつける形になる。昇級時のメッセージも数字を出さず「つぎは もうすこし むずかしいよ」と伝える。子どもが自分の状態を知る手がかりは、レベル番号ではなく問題そのものの手応え・ポイント・着せ替えの解放でよい。

### レベルの手動選択について

練習モードのレベルは選択制にせず、上記の自動昇降のみとする。

- 現在ポイントはレベル非依存（正解10pt + 全問正解50pt）なので、自由に選べると**Lv1を回すのが最適**になり、着せ替え目当てで一番簡単な問題を繰り返す行動を誘発する。ランキングをタイムアタック限定にしたのと同じ理由
- 「今日どのレベルをやる？」という選択は6歳児には負荷。数字PINパッドUIを選んだのと同じ判断

将来レベル数とスキル種別が増えたら（小2以降）、**到達済みレベルのみ選べる「ふくしゅう」の別導線・ポイントは半減または無し**という形で入れる余地がある。その場合はポイントのレベル別重み付けとセットで検討すること。

### 実装上の扱い（練習モード）

- **答えたら自動で次の問題へ進む**。1問ごとに「つぎへ」を押させるとテンポが悪く、10問やりきるまでのタップ数も倍になる。特に不正解のときに押させると、つまずいている子ほど操作量が増える逆向きの設計になる。押させたところで読解を強制できるわけでもない（急ぐ子は読まずに押す）
  - 待ち時間は**正解0.8秒／不正解2.5秒**。不正解は正しい答えに目をやる時間が要るので長めに取る
  - 「つぎへ」ボタンはどちらの場合も表示したままにする。待たずに進みたい子が押せるようにするため、かつボタンが消えると画面が動いて押し間違いを誘うため（[design.md](./design.md)）
  - 不正解の2.5秒は「じっくり考えたい子には短い」可能性がある。実機で子どもの様子を見て調整する前提の暫定値
- **1セッション = 10問**を単位として`practice_sessions`に1レコード記録し、そのタイミングでレベルアップを判定する。「もっとやる」で延長した分は次の10問＝別レコードとして記録する（結果画面を見たまま離脱しても、終わった10問の記録は残る）
- レベルアップした場合、次の10問から新しいレベルの問題になる（プレイ中に難易度が変わらないようにする）。降級も同様に次の10問から反映する
- 降級判定は今回のセッションを含む直近の記録を見るため、`practice_sessions`への記録→レベル変更の順で処理する。記録は必ず変更前のレベルIDで残る
- 最高レベルに到達済みの場合はレベルアップせず、そのレベルを繰り返す
- 出題レベルと獲得ポイントは**サーバー側で`child_progress`から導出**する。Server Actionは画面を経由せず直接POSTできるため、レベルIDや点数をクライアントの申告のまま信用しない

## モード設計

- **練習モード**（問題数ベース）: 日々の学習用。デフォルト10問、終了後に「もっとやる？」で+10問ずつ延長可能。ポイント・着せ替えアイテム解放に反映。ランキングには影響しない。プレッシャーなく自由に練習できることを重視する。フィードバックはフル（正解モーション・キャラ反応・獲得ポイント表示など）
- **タイムアタックモード**（60秒間固定）: ランキング専用モード。問題数の上限は設けず、時間切れまで出題し続ける。不正解には数秒のペナルティ（例: 3秒ロス）を課し、速さと正確さのバランスを取る。**5問連続正解するたびに3秒のタイムボーナス**を与え、正確に解き続けることにも報われるようにする（5問ごとに繰り返し発生し、不正解でリセットされる）。ペナルティと同じ秒数にしているのは、子どもにとって「3秒」を得も損も共通のものさしとして理解しやすくするため。スコア＝時間内の正解数。フィードバックは最小限（○✕を一瞬フラッシュ、ペナルティ時のみ「-3秒」、ボーナス時のみ「+3秒」を一瞬添える程度）で、テンポを止めない

## 着せ替えアバター

進化ではなく「人間のアバター1体＋着せ替えアイテム」方式。集める対象がキャラ丸ごとではなく着せ替えアイテムになる。

- ベースアバターは1体（見た目は最初にシンプルに選択）
- アイテムスロット: 髪型・トップス・ボトムス・ネックレス（データ駆動で今後追加可能。アクセサリーは抽象的すぎるため、まずネックレス1種類にミニマムに絞る。将来的に帽子・メガネなどを追加する場合は新しいslot_typeを足すだけでよい）
- 各アイテムに解放条件を個別設定できる（例: 累計正解100問／たし算Lv3到達／タイムアタック20点達成など）
- 新アイテム追加は図鑑にレコードを1件足すだけ（コード変更不要）
- 全身別キャラを複数描くより、ベース1体＋アイテム差分の方がアセット制作コストが低い。
- イラストはAI生成を活用してアセット制作コストを抑える

### 顔をえらぶ（肌の色・目・口）

「ベースアバターは1体（見た目は最初にシンプルに選択）」の実装。着せ替え（髪・トップス・ボトムス・ネックレス）は`wardrobe_items`の解放条件・ポイント経済に乗るが、顔は自己表現の土台であって「がんばって手に入れるもの」ではないため、あえて別軸にしている。

- `child_profiles.skin_tone` / `eye_style` / `mouth_style`（3列、`src/db/schema.ts`）
- ポイント不要・いつでも選び直せる。解放条件も無い（全パターン最初から選べる）
- 肌の色5種・目5種・口5種（`src/components/avatar.tsx`の`SKIN_TONES`/`EYE_STYLES`/`MOUTH_STYLES`）。からだの影色は肌の色から自動計算するので、肌の色を増やすときに影色を別途用意する必要はない
- 目・口の線の色は肌の色によらず固定（`FACE_LINE`）。どの肌の色でも読み取りやすくするため

### 入手のしかた（2種類）

`price_points`の有無で入手方法が変わる（[data-model.md](./data-model.md)）。

| `price_points` | 解放条件を満たすと |
|---|---|
| NULL | **その場で無料でもらえる**。練習の10問を終えた時点、またはきせかえ画面を開いたときに配られる |
| 数値 | **ポイントで交換できるようになる**。条件を満たしていないアイテムは、ポイントがいくらあっても買えない |

- スロットごとに`always`の無料アイテムを1つ置く。始めた日に着るものが無いとアバターが裸のままになるため（ネックレスは無くても成立するので除く）
- **条件のゆるい有料アイテムを必ず用意する。** 値段が付いたアイテムをすべて解放条件つきにすると、始めたばかりの子どもにはおみせに買えるものが1つも並ばず、ポイントが貯まるだけで使い道が無い状態になる（0002ではこれが起きていた）
- 初めて手に入れたスロットは自動で着せる。すでに着ているものは奪わない
- **到達レベルの条件は「今のレベル」ではなく「今までに到達した最高レベル」で判定する**。降級があるため現在レベルは下がりうるが、一度満たした条件が後から不成立に戻るのは子どもへの裏切りになる

### アイテムの階層（追加するときの目安）

練習10問で最大150ポイント（正解100 + 全問正解ボーナス50）が入ることを基準にする。

| 階層 | 解放条件 | 価格 | ねらい |
|---|---|---|---|
| はじめの1着 | `always` | 無料 | 始めた日に着るものを確保する |
| ふだんぎ | `always` 〜 低い`total_correct` | 100〜220 | ポイントの使い道。1〜2回の練習で買える |
| ごほうび | 中くらいの`total_correct` | 無料 | 練習の節目に「届く」もの。結果画面で知らせる |
| あこがれ | 高い`total_correct` / `level_reached` | 250〜600 | 長期の目標。条件を満たしてもさらにポイントが要る |

- **見た目の派手さは階層と揃える。** 目を引く華やかなアイテムは、あとから追加したときの驚きのために温存する。追加はマイグレーション1本で済むので、最初から全部出す必要はない
- 色違いは同じバリアントを使い回せばレコード追加だけで足りる（コード変更が要るのは新しい形を足すときだけ）

#### 現行の追加計画（積極案）

- 合計188件（T1:60 / T2:48 / T3:36 / T4:24 / T5:12 / T6:8）
- T1〜T6は`total_correct`中心で解放する。学年1〜6にまたがる長期運用で、難易度調整をしやすくするため
- 価格はティア内でも段階的に上げ、同ティアの後半ほど「少し先の目標」にする
- 上記とは別に、`always`（条件なし）でポイントだけあれば買えるアイテムを4スロット×12件・計48件追加する。T1〜T6を`total_correct`縛りに統一した結果、「ふだんぎ」階層が定義している`always`〜低い`total_correct`の下限（＝ポイントだけ貯めれば買えるもの）が新規分から抜け落ちていたため（0002で一度起きた「ポイントの使い道がない」状態の再発）。見た目は他の`always`アイテムと同じくT1（ベーシック）のみ、価格は100〜220（0003を踏襲）

### ティア別SVG制作テンプレート

実画像に置き換える前のSVG運用では、次のテンプレートを基準にティア感を揃える。

#### T1: ベーシック（現状踏襲）

```txt
{{アイテム名}}のSVGアイコンを作成してください。
- ベタ塗り2〜3色のみ、グラデーションなし
- 輪郭線は太さ均一のストローク1本
- 装飾は最小限(模様や柄は入れない)
- 現行の viewBox とレイヤー命名規則に準拠すること
初期装備らしい、シンプルで実用的な見た目にしてください。
```

#### T2: スタンダード

```txt
{{アイテム名}}のSVGアイコンを作成してください。T1からの主な変更点:
- 主要面に2色の linearGradient を1つ追加し、軽い立体感を出す
- 影を1箇所(裾・袖口など)、半透明の黒〜濃色オーバーレイで表現
- 輪郭線に強弱をつける(体の外側は太め、内側の切り替え線は細め)
- 単純な柄(ストライプ or 水玉)を1種類だけ追加可
色数は3〜5色に増やしてよい。派手さは抑えつつ「ちゃんとした装備」感を出す。
```

#### T3: クオリティ

```txt
{{アイテム名}}のSVGアイコンを作成してください。T2からの主な変更点:
- パーツを2層以上に分割(例: outfit_base の上に outfit_detail レイヤーを重ねる)
- radialGradient を使ってハイライトを1〜2箇所入れる(光源は左上45度で統一)
- 縁取りに二重線 or 装飾ステッチのようなディテールパスを追加
- clip-path を使い、柄(幾何学模様・花柄など)をパーツ形状にきれいに収める
- アクセサリパーツ(ボタン・リボン・宝石など)を1〜2個追加
色数制限なし。「お店で売っている装備」らしい作り込みにする。
```

#### T4: プレミアム

```txt
{{アイテム名}}のSVGアイコンを作成してください。T3からの主な変更点:
- 質感表現を追加(金属→ハイライト+ハイコントラストのグラデ、布→柔らかい多段グラデ、革→濃淡の縞)
- 装飾ディテールを3箇所以上(刺繍・宝石・金具・房飾りなど)
- アウトラインに部分的な光沢線(細い明色パス)を追加し、素材の質感を強調
- 全体のシルエットにアクセント(マント、羽根、大きめの装飾パーツなど)を1つ追加してよい
ポイントをしっかり貯めた子だけが手に入れられる、目を引く華やかさにする。
```

#### T5: スペシャル

```txt
{{アイテム名}}のSVGアイコンを作成してください。T4からの主な変更点:
- feGaussianBlur を使った発光エフェクト(グロー)をアクセントパーツに追加
- 発光色は主色の補色 or 金・虹色系を使い、特別感を演出
- アニメーション対応を前提にパーツを分割(例: 発光部分だけ独立した<g>にして、Framer Motionで明滅させられる構造にする)
- 特殊素材感(結晶・炎・氷・光の粒子など)をモチーフに組み込む
長く続けた子だけがたどり着ける段階だと一目でわかる、装備一覧の中で明らかに浮く見た目にする。
```

#### T6: デラックス

```txt
{{アイテム名}}のSVGアイコンを作成してください。T5からの主な変更点:
- パーティクル表現(小さな光の粒・星・火花など)を複数個、独立した<g>として追加し、Framer Motionで浮遊・明滅させる前提の構造にする
- グラデーション3種類以上を重ね、単色では出せない複雑な発色にする
- アイテム固有のシンボル(専用エンブレム・紋章など)を1つデザインし追加
- 可能であれば実装側でFramer Motionを使った常時アニメーションを想定した分割構造にする
いちばん長く頑張った子への、他のどのアイテムとも被らない一点物の存在感を出す。
```

### 画面での見せ方

**きせかえ（持っているものだけ）とおみせ（まだ持っていないものだけ）の2画面に分ける。** 上の報酬ループが中期＝ポイントで交換と長期＝集めてコーディネートを別の層として定義しているのに沿う。アイテムを多数用意する前提なので、所持済みと未所持が混ざった一覧はアイテムが増えるほどノイズになる。

- **一覧の並び順**は「きているもの → もっているもの → こうかんできる → ポイントがたりない → まだのもの」。一覧そのものが進み具合を語るようにする。同じ状態のなかでは安いものを先に出す（「つぎの目標」が上に来る）
- おみせではポイント帯フィルタ（例: 300まで / 301から700 / 701から1400 / 1401いじょう）で絞り込めるようにする。全件表示のままでも探しやすさを保つため
- **まだ手に入らないアイテムは名前も見た目も伏せる**（`？？？`）。見えていると手に入らないことへの不満が先に立つ。代わりに「なにをすれば もらえるか」だけを出す
- 無料開放のアイテムはおみせを開いた時点でも配る。タダでもらえるものが棚に並んでいると、交換の場としての意味がぼやけるため
- スロット切り替え・アイテムのタイル・ポイント表示は2画面で共通の部品を使う。見た目と操作感が違うと子どもには別のアプリに見えてしまう
- スロットが空のときは黙って空欄にせず、次の行き先を示す（きせかえ側は「おみせを のぞいてみよう」、おみせ側は「ぜんぶ てにいれたよ！」）
- アバターはマイページに常時表示する。着せ替えが長期の報酬として働くには、いつも目に入ることが前提
- **マイページを開くたびに、アバターがランダムなあいさつをする**（てをふる／ばんざい／ジャンプ／くるっと／おじぎ）。毎回おなじ動きだと2回目から目に入らなくなる。あいさつは一度やったら待機の揺れに戻す（ずっと動き続けていると視界の端がうるさい）
  - どれをするかは**サーバー側で引いてpropsで渡す**。Client Component側で`Math.random`を引くとSSRとハイドレーションで食い違う（出題生成と同じ理由）
- **アバターは練習中と結果画面にも出す。** マイページでしか会えないと、着せ替えても身につけている実感が薄い。練習画面ではレベル番号を外して空いた場所に小さく置き、行を増やさない（[design.md](./design.md)「スクロールなし方針」）
- **キャラクターは答えに反応する**（モード設計の「キャラ反応」）。正解＝跳ねる／不正解＝小さく首をかしげる／結果がよかったとき＝**ばんざい**（跳ぶのではなく、うでを上げて喜ぶ）。**不正解の反応で落ち込ませたり責めたりしない**（[design.md](./design.md): 恐怖感を与える演出は避ける）。成績が振るわなかった結果画面では、静かに待つだけにして祝わない代わりに沈ませもしない
- 動きを減らす設定（`prefers-reduced-motion`）では反応させない
- 新しく手に入れたアイテムは練習の結果画面で知らせる（中期の報酬ループの接点）

### アセットの扱い（現状）

実イラストがまだ無いため、`asset_ref`に「バリアント名 色」を入れ、コード側（`src/components/avatar.tsx`）がSVGの図形を描くダミー実装になっている。この形式なら同じ図形で色違いのアイテムを足すのがレコード追加だけで済み、「新アイテム追加はレコード1件」という方針を崩さない。実画像に差し替えるときは図形を`<image>`の重ね合わせに置き換える。

## ランキング設計

- スコアはタイムアタックモードの「時間内正解数」を使用する（練習モードのプレイ量そのものは反映しない。学習目的からズレた行動＝雑な連打を誘発しないため）
- **学年別セグメント必須**（1年生が6年生と同じ土俵で比較されないように）
- **週間リセット**（後から始めた子も上位を狙えるよう、全期間の一発勝負にしない）
- 見せ方はやさしく。自己ベストとの比較を主役にし、ランキングは「じょういグループだよ！」のような**言葉のバッジ**を基本にする。詳細な数値順位は任意で見られる程度に留める
  - 「上位◯%」のような%表記は避ける。対象学年の主戦場である小学校低学年はパーセントをまだ習っておらず、意味が伝わらないため（算数で習うのはもっと上の学年）
  - 内部の順位・パーセンタイル自体は計算するが、画面には出さず「じょうい／まんなか／これから」のような3段階程度の言葉に変換して見せる。境界値の細かい調整より、この変換をやめない（%を出さない）ことの方が優先度が高い
  - 1〜3位は参加人数によらず常に最上位の言葉にする。参加者がまだ少ない学年・立ち上げ初期はパーセンタイル計算だけだと「1位なのに上位グループにならない」ことが起きるため

## 自己ベスト

- タイムアタックモードのスコア記録。自分のみに表示（安全）

## 表示用ニックネーム（ランキング用）

- ログイン用IDとは別に、プロフィール作成時にシステムが自動生成する
- 自由入力にしない（不適切な文字列のモデレーションが不要になる）
- ログインIDをそのまま公開しない（IDが割れるとPIN総当たりの的を絞られてしまうため）

**生成方式**: 形容詞＋名詞（動物など）＋数字3桁のランダム組み合わせ（例:「げんきなトラ402」）

- 組み合わせ数を十分広く取る（例: 形容詞40種×名詞40種×数字900通り ≒ 144万通り）ことで実用上の衝突はほぼ発生しない
- `nickname`カラムに`UNIQUE`制約を設定
- 生成時は「先にINSERTを試みて、重複エラーが返ったら再生成してリトライ」する方式にする（SELECTで存在確認してからINSERTすると競合状態のリスクがあるため）
